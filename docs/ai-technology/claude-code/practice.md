# 使用实践

<span class="dig-tag dig-tag--category">Claude Code</span> <span class="dig-tag dig-tag--hard">进阶</span>

::: tip 核心要点
有效使用 Claude Code 的顺序是：**准备可复现环境 → 提供项目约定 → 明确任务和权限 → 小步修改并验证 → 审查交付物**。先把单个任务做可靠，再增加子 Agent、MCP 和自动化。把官方能力用在它负责的层次：指令指导行为，配置改变运行方式，审批控制动作，测试检查结果。
:::

## 1. 准备环境

### 安装与认证

使用[官方安装方式](https://code.claude.com/docs/en/setup)。Windows 可通过 WinGet 安装；以下是读者自行执行的 PowerShell 命令：

```powershell
winget install Anthropic.ClaudeCode
```

安装完成后，在新终端检查版本和安装状态：

```powershell
claude --version
claude doctor
```

进入要处理的项目目录后运行 `claude`，按官方流程完成认证。订阅登录、Console API 用量以及第三方模型接入有不同条件，不应把个人交互登录方式直接复制进团队 CI。自动化凭据应由秘密管理系统注入，不能写入项目指令、提交记录或调试日志。

Windows 的 Shell 工具选择取决于安装环境与版本；需要 Bash 工作流时准备 Git for Windows，使用 WSL 时则按 Linux 环境处理。确认 Java、Node.js、数据库等项目依赖同样可用：**Claude Code 安装成功，不代表项目已经能够构建**。

### 工作目录决定什么

从哪个目录启动，会影响搜索范围、项目指令发现、相对路径、会话归属与命令执行。多模块工程应选与任务相符的工作目录，并明确需要访问的其他目录。

工作目录不是沙箱。即使在临时目录启动，子进程仍可能继承环境变量和账户能力。涉及敏感项目时，应单独控制文件访问、网络、凭据和操作系统身份。

### 先确认基线

开始修改前记录当前分支和已有改动，运行一次任务相关的最小检查。这样才能区分“原先就失败”“环境无法执行”和“本次修改引入失败”，也能避免误覆盖开发者尚未提交的文件。

## 2. 配置项目约定

### 项目指令写什么

CLAUDE.md 适合写那些开发者需要反复解释、又不能轻易从代码推断的约定：特殊测试命令、不能修改的兼容契约、生成文件的处理方式、环境陷阱。

例如，一个假设使用 npm 的 TypeScript 项目，可以写成：

```text
项目约定
- 修改接口时保持已有错误码，不改变字段命名。
- 单元测试使用 npm test；类型检查使用 npm run typecheck。
- 生成目录不直接编辑，先修改对应输入文件。
- 先运行相关测试，完成后报告实际执行的命令和结果。
- 不提交、不推送、不部署，除非本次任务明确要求。
```

这些命令必须替换为项目实际支持的命令。不要让 Agent 根据一份过期的模板反复安装工具或修改构建配置。

### 指令分层不等于配置覆盖

用户级、项目级与子目录级指令服务不同范围；子目录内容可以按工作路径加载。多份指令进入上下文后，不等于配置对象按键覆盖，更不能保证冲突时模型必然选择某一条。

共享规则应保持一致；只适用于某类文件的约定放在路径范围明确的规则里；多步骤任务方法放在 Skill 中。用 `/context` 检查实际加载内容，用 `/memory` 查看和管理相关文件。

较新版本支持在指定条件下加载 AGENTS.md；直接加载能力从 CLI v2.1.277 起提供，且受指令配置影响。跨工具共享约定时，应按[官方加载规则](https://code.claude.com/docs/en/memory)验证，不要仅凭文件存在就认定已经生效。

### settings 负责运行配置

常见配置位置包括用户级 `~/.claude/settings.json`、项目级 `.claude/settings.json` 和本地项目配置 `.claude/settings.local.json`。组织托管策略具有单独的强制边界，不应由普通项目配置绕开。

下面的 JSON 是一个从手动审批起步的示例，放行工作目录下的部分读取能力，并拒绝读取 `.env` 类文件：

```json
{
  "permissions": {
    "defaultMode": "default",
    "allow": ["Read", "Glob", "Grep"],
    "deny": ["Read(./.env)", "Read(./.env.*)"]
  }
}
```

它**不是完整的秘密防泄漏策略**：Shell、外部服务、继承的凭据与其他文件路径也可能接触敏感数据。路径规则应按其来源、相对路径语义和实际 CLI 版本测试，必要时使用沙箱与独立执行环境。

## 3. 完成一个可验收的任务

### 描述输入、边界与输出

“修一下分页”没有说明预期行为。更好的任务包含失败现象、范围、兼容约束和验收方式：

```text
分页接口在总记录数恰好等于页大小时遗漏末条记录。
先阅读分页实现和对应测试，给出原因及最小修改方案。
确认后补充边界测试并修复，不改变响应字段，不升级依赖。
验证空集合、恰好一页、超过一页三种情况。
结束时报告改动文件、实际测试结果和未验证项。
```

这个描述并不预先指定 bug 一定在哪里，而是提供了能够反驳错误假设的检查。

### 何时使用 Plan

范围不清、涉及多个模块或需要协调方案时，可以用 `claude --permission-mode plan` 开始，先探索和确认设计。Plan 模式仍会使用读取和搜索能力，不是关闭所有工具；在 SDK 等入口中还要防止审批逻辑意外批准写操作。

明确的小修改不必先生成庞大计划。任务越小，越应尽早形成局部假设并运行一个便宜的检查。

### 修改与验证形成短循环

1. 通过测试或稳定步骤复现失败。
2. 读取直接控制行为的实现和相邻调用点。
3. 进行最小修改，不顺手清理无关代码。
4. 先重跑对应检查，再按影响范围增加回归验证。
5. 审查 diff，确认没有删测试、放松约束或改变公共契约。

前端任务还应检查浏览器中的真实页面和不同视口；后端任务应区分单元测试、依赖模拟和真实接口调用。命令没跑起来时，需要报告阻塞原因，不能写成“已验证”。

## 4. 管理权限与会话

### 选择权限模式

| 模式 | 用途 | 需要注意 |
|------|------|----------|
| `default` | 从普通审批流程开始 | 具体动作是否需要确认还受规则、工具与路径影响 |
| `plan` | 先探索与拟定方案 | 不是 OS 只读隔离，也不是全部工具禁用 |
| `acceptEdits` | 自动批准范围内的文件操作 | 不仅仅涉及编辑器中的字符串替换 |
| `dontAsk` | 无人值守时拒绝本应询问的动作 | 不会自动删除所有未列入 allow 的工具 |
| `auto` | 在支持条件下使用自动风险判断 | 可用性和分类器决策不等于完整安全保证 |

不要以跳过权限检查作为解决卡住任务的默认办法。先确认任务为何被拒绝，是否真的需要这项能力，再缩小授权范围。模式与规则的实现见后续工具章节。

### 恢复、压缩和回退各做什么

- `claude --continue`：继续当前目录相应范围内最近的会话；不要在自动化中用它猜测任务身份。
- `claude --resume`：选择会话；确定性脚本应记录并使用具体会话 ID。
- `/compact`：压缩上下文，适合继续同一长任务，不是删除所有历史数据。
- `/clear`：为无关任务清理当前上下文；与数据删除、文件恢复不是一回事。
- `/rewind`：按可用检查点恢复相应对话或文件状态；不覆盖所有 Shell 和远程副作用。

恢复之后要重新检查真实文件和环境。会话记得“测试已通过”，不能证明当前分支、依赖或文件仍然是当时的状态。

### 控制上下文与费用

按需读取文件、限制工具输出、把无关探索交给独立任务，有助于减少噪声。不要反复把完整日志贴回会话，也不要同时加载与任务无关的大量工具描述。

轮数、上下文大小、输出 Token、金额预算与墙钟时间是不同资源。自动化应同时考虑运行预算和外层超时；客户端费用估算还可能超出阈值，不能当成精确账单硬上限。

## 5. 选择扩展机制

| 需求 | 适合的能力 | 使用前检查 |
|------|------------|------------|
| 每次都遵守项目约定 | CLAUDE.md 与规则 | 是否简短、可验证、没有冲突 |
| 重复执行一套任务方法 | Skill | 触发条件、参数、步骤和验收标准 |
| 调用外部系统 | MCP 或现有 CLI | 身份、权限、输入输出及敏感数据边界 |
| 在指定事件执行检查 | Hook | 事件时机、输出契约、超时和失败策略 |
| 隔离一段探索或审查 | 子 Agent | 输入是否完整、工具是否足够、结果如何汇总 |
| 分发一组能力 | 插件 | 配置来源、所含脚本、凭据和启停影响 |

先添加一个真正需要的能力，并观察它是否被正确加载和调用。不要把“安装了多个插件”当作质量改进的证明；扩展会同时增加配置、上下文、权限和故障面。

例如，已有可审计的内部 CLI 时，不一定需要再包一层 MCP；只想重复使用审查清单时，也不需要为了 Skill 额外搭建服务。

## 6. 脚本与 CI

### 从受限的单次任务开始

`-p` 表示非交互运行，而不是关闭 Agent 循环。下面用明确工具集合、MCP 拒绝规则和预算运行一次读取任务；该命令需要读者已完成认证，会产生模型用量：

```powershell
claude -p "Read README.md and summarize the project purpose." --tools "Read,Glob,Grep" --allowedTools "Read,Glob,Grep" --disallowedTools "mcp__*" --permission-mode dontAsk --max-turns 4 --max-budget-usd 1 --output-format json
```

`--tools` 主要控制内置工具，不能单靠它排除 MCP 工具；`--allowedTools` 则是自动批准规则，二者含义不同。项目自定义 Hook 等启动行为也需要单独审查。自动化应在不含生产凭据的受控工作环境运行，而不是把上面一行命令当成完整隔离措施。

需要观察中间进度时，将输出格式改为 `--output-format stream-json --verbose`。这会输出逐行 JSON 消息，而不是一份逐 Token 的纯文本答案。

### 三层验收

**进程层**检查退出状态、超时和是否被取消；**协议层**检查 result 的错误标志、终止原因和输出结构；**业务层**检查补丁与验收测试。任何一层失败都不能被另一层“成功”掩盖。

多个任务并发时，应使用不同工作目录或 worktree，记录任务 ID 与会话 ID 的对应关系。不要让多个进程同时修改一份 checkout 或向同一会话追加历史，再期待最后一条回答自动代表全部结果。

### CI 的边界

只提供本任务需要的凭据与网络权限；对来自不可信提交的脚本和安装钩子保持隔离。将生成的变更交付为待审查补丁或 PR，不要默认把测试通过等同于允许部署。

## 7. 排错与交付

| 现象 | 优先检查 |
|------|----------|
| 无法启动或找不到命令 | 安装路径、终端刷新、版本与 `claude doctor` |
| 反复询问或拒绝动作 | 当前模式、规则来源、路径范围、是否无人能审批 |
| 项目约定没有生效 | 工作目录、实际加载内容、指令来源和相互冲突 |
| 读取很多但没有进展 | 任务范围、关键证据和最小验收检查是否明确 |
| 中断后接续结果混乱 | 会话 ID、未完成任务、消息消费与文件实际状态 |
| 结果正确但费用很高 | 重复读取、大量工具描述、输出噪声、子任务重复工作 |

交付时至少说明：改了什么、运行了什么检查、结果如何、还有什么没有验证。需要保留的跨任务经验应是短而具体的事实，不是把本轮所有日志都写进长期记忆。
