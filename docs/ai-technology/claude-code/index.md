# 概念与对比

<span class="dig-tag dig-tag--category">Claude Code</span> <span class="dig-tag dig-tag--hard">进阶</span>

::: tip 核心要点
Claude Code 是围绕 Claude 模型构建的编程 Agent：它能根据目标搜索项目、修改文件、执行命令，再根据结果继续行动。理解它，不能只看模型能力，也不能只看终端界面；关键是**模型决策、上下文供给、工具执行、权限控制与结果验证**如何共同工作。与 Codex、Cursor、GitHub Copilot 比较时，应比较具体工作形态，而不是把品牌名称当成固定架构。
:::

## 1. Claude Code 是什么

### 从生成代码到完成任务

代码补全通常回答“这里接下来写什么”，聊天助手通常回答“这个问题怎么解决”。编程 Agent 接受的则可以是一个有验收条件的任务，例如：

> 找出分页接口遗漏最后一条记录的原因，补充回归测试，修复后运行相关测试；不要改变接口格式。

Claude Code 可以先定位接口与测试，再读取实现、修改文件、运行测试，必要时根据失败结果调整。最终产物不只是回答，也包括工作目录中的补丁和可核验的执行结果。

这里的“自主”是**在权限和预算内选择步骤**，不是无限执行，也不意味着每次都会自动写出正确测试。一个长任务可能因缺少需求、权限拒绝、网络错误、预算耗尽或用户中断而暂停。

### 模型、产品和 SDK

| 对象 | 主要职责 | 不应混淆的概念 |
|------|----------|----------------|
| Claude 模型 | 根据输入产生文本、推理相关输出和工具调用 | 模型不会仅凭生成一段命令就修改本地文件 |
| Claude Code | 提供执行循环、工具、上下文、权限、会话和交互 | 不是一条 System Prompt，也不只是 API 转发器 |
| Claude Agent SDK | 让应用通过编程接口驱动相应运行能力 | SDK 客户端的消息循环不等于完整的模型决策循环 |
| Skills、MCP、Hooks | 分别补充任务方法、外部能力和生命周期处理 | 三者互不替代，指令文本不能替代宿主权限策略 |

因此，同一个模型放进不同工具环境、获得不同上下文和验证反馈，最终表现可能不同。评价模型与评价整个编程系统，必须分开设计实验。

## 2. 一次任务怎样完成

可以用五个动作理解工作过程：

```text
明确目标与限制
  → 搜索、读取与建立局部理解
  → 提出下一步动作
  → 权限检查后执行工具
  → 用结果决定继续、修正、询问或结束
```

### 搜索不是“全项目已经读过”

能够访问整个项目，不代表整个项目已进入模型上下文。Agent 通常先按名称、符号或文本搜索，再读取相关片段。目录结构、项目指令、类型信息和测试结果共同帮助它缩小范围。

这与传统 RAG 并非只能二选一。关键词搜索、语义检索、语言服务和直接文件读取可以组合；不能从某次使用了 Grep，就推导出所有版本、所有入口都完全不用索引。

### 工具反馈推动下一步

测试失败不是普通日志，而是下一轮决策的输入。模型可能据此判断：需要修改实现、修正测试假设，还是先处理环境问题。

但反馈只有被正确解释才有用。“进程退出码为 0”“模型说已修复”“运行结束”分别属于不同层次；真正验收需要检查用户要求是否满足、测试是否覆盖原问题、是否引入非预期改动。

### 人仍然在控制链中

任务开始时，人提供目标和边界；执行时，人可以批准敏感动作、补充信息或中断；交付时，人审查补丁和证据。更好的自主执行通常来自更清楚的验收条件，而不是更宽泛的工具权限。

## 3. 与 Codex 对比

这里的 Codex 指 OpenAI 的编程产品，重点比较 **Codex CLI 与 Claude Code 的本地编程工作流**。两者均有其他使用入口，不能把 Codex 等同于云端任务，把 Claude Code 等同于只有终端。

| 维度 | Claude Code | Codex |
|------|-------------|-------|
| 本地交互 | 终端中探索、修改、执行与验证，也有 IDE 等入口 | CLI 中探索、修改、执行与验证，也有 IDE 等入口 |
| 核心执行方式 | 模型在运行时约束下选择工具并持续处理反馈 | 同样围绕模型、工具、上下文与反馈形成任务循环 |
| 项目约定 | 以 CLAUDE.md、规则和相关配置承载项目知识 | 以 AGENTS.md 和相关配置承载项目约定 |
| 权限控制 | 权限模式、工具规则、审批与支持环境下的沙箱 | 审批策略、沙箱与可写范围等控制 |
| 扩展与自动化 | Skills、MCP、Hooks、插件及 Agent SDK 等 | Skills、MCP、配置化扩展及非交互执行等 |
| 远程任务 | 云端任务与本地 Remote Control 是不同执行位置 | 云端任务与本地 CLI 也需要区分执行位置 |

<small>能力对照基于 2026-10-18 的官方说明；具体入口、账户和版本会影响可用范围。</small>

### 真正值得比较的差异

**第一，工作流是否适合团队。** 团队主要在终端、IDE，还是通过 issue 和 PR 委派任务？审批放在哪里，结果在哪里审查？这些差异比“有没有聊天框”更重要。

**第二，能否获得同等质量的上下文。** 同一任务若一方拿到完整失败日志与项目指令，另一方只有一句描述，测到的是输入差异，不是产品差异。

**第三，权限和环境是否一致。** 能运行测试的 Agent 通常比只能阅读的 Agent 更容易得到反馈。不能把“允许联网安装依赖”与“隔离且无网络”环境下的结果直接横向比较。

**第四，完成质量与成本。** 分别记录补丁正确率、首次验证通过率、人工修正时间、任务时长和模型用量；不要用一次成功示例或单一排行榜下结论。

### 不做永久的“谁更聪明”结论

实际效果随模型版本、推理配置、任务类型、上下文和工具环境变化。更可迁移的判断是：在团队自己的任务样本、相同权限与验收标准下，哪种组合更稳定、可审查、易恢复。

## 4. 与 Cursor、Copilot 对比

### Cursor：从编辑器工作流看

Cursor Agent 能搜索、编辑、运行终端命令并根据结果继续执行，不能把它描述成仅逐条给建议的聊天插件。它与编辑器、代码浏览和变更审查的结合，是日常体验的重要部分。

如果团队高度依赖选区、跳转、内联 diff 和连续的小步修改，编辑器集成质量是重要评估项。若主要通过脚本批量处理独立任务，则应比较非交互入口和自动化契约，而不是只比较编辑器外观。

### GitHub Copilot：区分两种 Agent

**IDE 内的 Agent** 与开发者共享编辑器和本地工作流，能够使用相应工具修改代码、执行检查并迭代。

**云端 coding agent** 则侧重把任务交给远端执行环境，并通过分支、PR、检查和 review 交付。运行环境、凭据、联网策略与审批路径需要单独确认。

不能把两者合并成“Copilot 只在云端虚拟机运行”，也不能把一个远端隔离环境表述为对所有风险的完全隔离。

### 选型从协作方式出发

| 工作场景 | 优先检查 |
|----------|----------|
| 与开发者共同调试 | 中断与纠偏、局部上下文、终端反馈、diff 审查体验 |
| 委派独立任务 | 环境可复现、任务状态、分支隔离、结果交付与通知 |
| 企业内网项目 | 模型接入、数据流向、代理与认证、策略管理、审计 |
| CI 自动化 | 结构化结果、退出状态、预算、超时、幂等和凭据范围 |
| 多任务并行 | 工作目录隔离、共享资源冲突、资源成本、合并与回归检查 |

## 5. 怎样衡量一个编程 Agent

### 用任务集代替印象

准备覆盖团队真实工作的任务：局部 bug 修复、补测试、跨文件小功能、依赖升级、行为保持重构。为每个任务记录初始版本、环境、验收命令、允许修改范围和不得改变的契约。

同一个任务可以重复运行，避免把一次偶然结果当成稳定能力。测试集也应包含隐藏用例和边界条件，不能只让 Agent 编写自己的验收标准。

### 观察结果，也观察过程

1. **结果正确性**：测试通过、边界处理正确、没有规避需求。
2. **修改范围**：没有删测试、放宽断言或顺手改动无关文件。
3. **执行约束**：没有越权出网、读取敏感内容或跳过审批。
4. **恢复能力**：中断、工具失败或上下文压缩后能否正确继续。
5. **人工成本**：审查、纠错和重新提供上下文需要多少工作。

一个系统即使最后修好了代码，若过程执行了未授权动作，也不能算合格；反过来，因合理权限限制而暂停，也不应自动判为模型失败。

## 6. 学习路线

本专题先建立产品概念和使用方式，再按运行机制、工具与权限、上下文与会话、协作与扩展四个主题深入实现。主线始终是一条可检查的任务，而不是背诵模块名或功能数量。

1. **概念与对比**：本页，明确产品定位、工作方式与选型维度。
2. **[使用实践](./practice)**：从官方能力建立可验收的日常工作流。
3. **[运行机制](./runtime)**：启动、输入处理、主循环、模型流与终止路径。
4. **[工具与权限](./tools)**：工具契约、并发调度、文件一致性、审批与隔离。
5. **[上下文与会话](./context)**：Prompt、缓存、压缩、记忆、持久化与恢复。
6. **[协作与扩展](./extensions)**：子 Agent、MCP、Skills、插件和宿主接口。

通用概念可先阅读 [AI Agent](../ai-agents) 与 [Harness Engineering](../harness-engineering)。理解具体产品时，再分别追问：**谁拥有状态、谁决定动作、谁执行副作用、失败由谁处理**。
