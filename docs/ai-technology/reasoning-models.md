# 推理模型与测试时计算

<span class="dig-tag dig-tag--category">AI 技术</span>

::: tip 核心要点
推理模型与测试时计算关注的是：**回答同一道题时，额外计算怎样转化为更高的任务成功率**。训练可以改变模型的策略，部署时可以调整思考预算、采样、搜索和验证，但“想得更久”不自动等于答案更可靠。必须同时评估质量、延迟、费用与副作用。
:::

> 内容核对：2026-10-15。推理参数、内部状态重放和计费随模型/API 变化；本文区分通用机制与产品接口，不维护型号排行榜。

## 先区分三个容易混淆的“推理”

| 术语 | 指什么 | 例子 |
|------|--------|------|
| **模型推断 Inference** | 运行模型得到输出 | 一次分类、文本生成或图像编码 |
| **任务推理 Reasoning** | 分解、推导、比较和验证任务 | 查清订单异常原因、证明结论 |
| **测试时计算 Test-Time Compute** | 在使用模型时增加计算投入 | 更长思考、多个候选、搜索与验证 |

推理引擎优化主要解决“同样的工作如何更快、更省”，本章解决“要不要多做一些工作、做什么工作”。两者可以同时发生，但不是一回事；KV Cache、量化与批处理见 [推理优化](./inference-optimization)。

## 推理模型改变了什么

推理能力不是只属于名为 Reasoning 的模型，普通语言模型也能完成推理任务。产品通常用“推理模型”描述经过相关后训练、能分配更多内部计算解决多步骤问题的模型或运行模式。

这不意味着换掉了自回归生成机制，更不意味着内部文字就是忠实的逻辑证明。外界能够验证的是答案、执行结果和可观察行为，不能根据一段看似严密的解释推断隐藏实现。

| 概念 | 改变权重吗 | 主要发生在哪个阶段 |
|------|------------|--------------------|
| 推理轨迹 SFT | 是 | 训练：从示例学习行为 |
| RLVR / 在线强化学习 | 是 | 训练：通过可验证奖励改善策略 |
| CoT 提示 | 否 | 使用时：提示分步表达 |
| 思考预算 / effort | 否 | 使用时：控制或引导计算投入 |
| Best-of-N / 搜索 | 否 | 使用时：增加候选并选择 |
| 外部工具验证 | 通常否 | 使用时：从测试、查询或环境获得证据 |

RLVR 是奖励信号的选择，GRPO 是优化算法，二者不应与部署时“多采样几次”混为一谈。训练细节见 [模型训练](./model-training)。

## 三种增加测试时计算的方法 {#test-time-compute}

### 串行：让一个候选走得更深

模型围绕同一任务继续分解、核对、修正或调用工具。适合步骤有依赖的任务，例如定位 bug 后再设计修复。代价是关键路径变长，错误也可能沿路径传播。

在已经支持内部推理的模型上，不必机械添加“请输出全部思考过程”。更有效的输入通常是目标、约束、可用证据和验收条件；需要解释时要求简洁依据与可验证结果。

### 并行：生成多个候选再选择

Best-of-N 先生成候选，再由评分器选择；Self-Consistency 常对可规范化的最终答案投票。两个方法都要求定义“比较什么”，并考虑候选之间的相关错误。

```text
同一问题
  -> 候选 A -> 校验
  -> 候选 B -> 校验
  -> 候选 C -> 校验
  -> 按预先定义的规则选择或拒答
```

对于相互独立、单次正确率都为 $p$ 的理想候选，至少一个正确的概率为：

$$
P(\text{至少一个正确})=1-(1-p)^N
$$

若 $p=0.6$、$N=4$，这个概率是 $97.44\%$。但这**不是最终输出准确率**：真实候选不一定独立，评分器还可能选错，多数票也可能选择共同的错误答案。它更接近“候选集中存在可用答案”的机会。

### 搜索：在候选与验证之间交替

搜索不是一次生成 N 份完整答案，而是探索部分路径，验证后继续、剪枝或回退。Tree-of-Thought 等方法可以按显式状态组织搜索，但分支增长和不可靠评分会迅速放大成本。

并非每个推理模型都在内部执行某种已知搜索算法。未披露的内部机制与应用自己实现的搜索必须分开描述。

## 验证器决定额外计算是否有价值 {#verifiers}

| 验证方式 | 更适合什么 | 仍然可能错在哪里 |
|----------|------------|------------------|
| 单元测试、编译、约束求解 | 代码、格式、可形式化约束 | 测试覆盖有限，可能被“只过测试”的方案利用 |
| 数学或业务规则 | 金额、日期、精确字段、边界条件 | 规则遗漏，输入证据本身错误 |
| 权威来源与外部状态 | 搜索事实、实际订单、操作是否生效 | 来源过期，查询权限或一致性问题 |
| ORM / PRM | 候选排序、结果或过程评价 | 奖励偏差，分数不等于概率 |
| LLM-as-Judge | 开放式报告、表达与综合质量 | 位置、风格、冗长、自我偏好及注入 |

**模型说“我很确定”不是置信度校准**。可靠性需要在标注集上验证分数与实际错误率之间的关系；高风险动作仍由确定性权限与审批控制，不能用推理分数替代。

生成更多候选还可能更容易找到“骗过验证器”的候选。奖励和验证指标必须与真实目标一致，并保留独立的测试与人工复核。

## 实战：修复一个并发 bug

单次生成可能给出“增加重试”的修复，但正确方案需要证明不会重复写入。一个有界流程可以是：

1. 先复现失败，记录约束：不得修改公共 API，不得取消幂等保护。
2. 让模型提出局部假设，读取控制并发行为的代码。
3. 若要比较多个候选，在隔离工作区运行，不让候选同时修改同一分支或生产系统。
4. 用原失败用例、重复请求用例与回归测试验证，比较副作用和变更范围。
5. 选择满足约束的最小修复；都未通过时报告未完成，不以“得分最高”代替合格。

这同时使用了模型推理、工具和 Harness。测试时计算提高的是尝试与验证的机会，可靠性仍依赖任务定义与环境证据。

## API 中的预算、状态与输出 {#runtime-budget}

### effort 不是精确 Token 配额

不同供应商可能提供 reasoning effort、thinking level、自适应思考或独立运行模式。支持的档位和默认值依型号而变，同名 `high` 不代表相同计算量，也不能直接映射成固定 Token 数。

应分别记录：模型/快照、推理档位、最大输出、候选数、工具次数、总截止时间与总费用。并行候选可能减少等待时间，但不会免除总计算成本；工具与排队也可能成为真正瓶颈。

### 输出预算可能在可见答案之前用完

一些 API 把内部 reasoning tokens 计入输出用量和输出上限。下面是示意 usage，不是所有供应商共有的字段：

```json
{
  "input_tokens": 1000,
  "output_tokens": 2400,
  "output_tokens_details": { "reasoning_tokens": 1800 },
  "total_tokens": 3400
}
```

这里的 1800 是 2400 的子集，不应再加一次成为 4200 输出 Token；剩余部分也未必全部是用户可见文字。应按 API 语义计费，避免把内部推理既计入输出又重复收费。

模型可能因达到上限返回不完整响应，甚至还没给出可见答案。应用需检查完成状态、拒答、截断和工具结果，而不是只读取 `output_text`。预算耗尽后不应无条件重试，更不能执行不完整的动作参数。

### 会话消息与推理状态不同

OpenAI 等 API 可以返回不透明的 reasoning item，并提供继续会话或重放机制。这些对象不是应展示给用户的原始思维链，也不应自行修改、伪造或当作跨供应商通用状态。

有工具调用时，保留 API 要求的关联 ID、工具结果、消息阶段及推理项；跨模型族切换要检查兼容性。人工摘要可以帮助恢复业务目标，但不能代替供应商要求的协议对象。具体行为见 [OpenAI Reasoning 文档](https://developers.openai.com/api/docs/guides/reasoning)。

## 怎样选择计算预算 {#budget-selection}

把问题写成受约束的选择，而不是默认最高档：

$$
\min_{c\in\mathcal C}\mathbb E[Cost(c)]
\quad\text{s.t.}\quad Quality(c)\ge Q_{min},\quad Latency_{P95}(c)\le L_{max}
$$

这里的配置 $c$ 包含模型、effort、候选数、验证器和工具预算，质量与延迟必须通过业务评测估计。安全和权限约束是额外硬门槛，不能用更高平均质量抵消越权。

一个合理的升级顺序是：先检查缺失信息和错误工具，再修正上下文与验收条件，然后比较更高 effort、更多候选或更强模型。缺少订单信息时，增加思考不如调用订单 API；任务本身不允许执行时，任何档位都不能解决授权问题。

| 任务 | 可尝试的起点 | 什么时候升级 |
|------|--------------|----------------|
| 分类、格式抽取 | 低延迟配置 + Schema/规则 | 难例切片显著不达标 |
| 代码调试 | 有界推理 + 测试反馈 | 当前证据下仍不能定位，且预算允许 |
| 多源研究 | 检索 + 来源核对 + 综合 | 跨资料矛盾需要进一步验证 |
| 不可逆业务动作 | 确定性流程 + 授权/审批 | 不用提高 effort 绕过流程 |

## 评测时不能只看最高分

固定任务集、模型快照、工具环境、上下文、验证器和预算，分别测串行投入、候选数与模型升级。比较任务成功率、违规动作、超时、P95 延迟和每个成功任务的总成本。

同时记录候选中“至少一个通过”与最终选择“真的通过”的差距，它能揭示瓶颈在生成还是验证。增加计算后质量下降时，检查过度探索、错误反馈、超时和超范围修改，而不是假设系统测错了。

## 面试怎么答

**Q：Reasoning model 和普通 LLM 的本质区别是什么？** 通常是后训练与使用时计算策略的差异，不是能否生成语言，也不是必须换一种骨干架构。能力要按任务与预算衡量。

**Q：为什么多采样不能直接保证正确？** 候选会相关，验证器会误判，选择最优分数还可能放大奖励漏洞。要测最终选择的质量，而不只测候选覆盖率。

**Q：怎样控制成本？** 用质量与延迟门槛选择最低成本配置，限制整个任务的计算与工具预算；失败重试、候选和验证器费用全部计入。
