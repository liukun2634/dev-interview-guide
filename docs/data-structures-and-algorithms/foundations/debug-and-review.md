# 调试技巧

<span class="dig-tag dig-tag--category">基础知识</span> <span class="dig-tag dig-tag--easy">⭐ 入门</span> <span class="dig-tag dig-tag--hot">🔥 高频</span>

::: tip 💡 核心要点
很多题不是不会，而是写出来后不够稳定。要把做题能力变成可复用能力，必须建立固定的调试顺序、复盘模板和错题整理方法。
:::

## 概念

- 调试的目标不是盲目加打印，而是尽快定位哪一步的状态偏离了预期。
- 复盘的目标不是重抄答案，而是记录这题的触发信号、关键做法和易错点。
- 错题整理的重点不是数量，而是让你下次看到同类题能更快识别。

## 怎么处理

### 写完题后的固定检查顺序

1. 先过最小样例：空数组、单元素、全相同、严格递增、严格递减。
2. 再过边界样例：重复值、负数、极大值、极小值、越界位置。
3. 如果是双指针、窗口、队列或递归，手推关键状态变化。
4. 最后再决定是否加打印，不要一上来就把日志打满。

### 复盘时至少记录三件事

1. 这题的题型信号是什么。
2. 这题为什么能想到这个方法。
3. 这题最容易写错的边界在哪里。

## 错题记录模板

| 记录项 | 建议内容 |
|------|------|
| 题目类型 | 数组、图、树、DP、贪心 |
| 触发信号 | 有序、连续区间、最短步数、Top K、依赖关系 |
| 正确方法 | 双指针、BFS、堆、拓扑排序、动态规划 |
| 卡点 | 没看出题型、复杂度判断错误、代码实现不稳 |
| 易错点 | 边界处理、重复元素、初始化、下标越界 |

## 最常见的排错点

1. 数组和字符串题，先查下标边界与循环条件。
2. 哈希题，先查 key 是否设计对了，更新时机是否正确。
3. 树和图题，先查 visited、递归返回值和终止条件。
4. 动态规划题，先查状态定义、初始化和遍历顺序。

## 这一页的目标

- 让你写完题后不是凭感觉检查，而是按固定顺序收口。
- 让错题本记录的是“可迁移的方法”，不是零散代码片段。

## 暴力对拍：验证优化没有改变答案

对拍不是“多跑几个样例”，而是用一个小规模下可靠、思路独立的实现作为答案来源。优化代码错在哪里，往往只有在重复值、负数或特殊更新次序下才显现。

| 优化算法 | 小规模参照 | 除答案外还应检查 |
|----------|------------|------------------|
| 树状数组求逆序对 | 两层循环枚举每一对下标 | 重复值共享排名，相等不计逆序 |
| 最短子数组的单调队列 | 枚举所有区间并累加 | 负数、无解、long 前缀和 |
| LIS 二分 + 前驱恢复 | O(n²) DP 求长度 | 输出严格递增，且按原数组顺序出现 |
| Dijkstra / 0-1 BFS | 小图 Floyd | 不可达、自环、零权边、恢复路径的权重 |
| Tarjan SCC | 每点搜索或传递闭包 | 两点同组当且仅当互相可达，节点不能遗漏或重复 |
| LFU | 每次淘汰扫描全部 key，按频次再按最近访问时刻比较 | 容量限制、桶非空、最小频次与同频顺序 |

**固定流程**：先穷举很小的值域，再用固定随机种子生成稍大的实例；每次失败打印完整输入、种子与实际/期望答案。把失败输入继续删元素、删边，直到得到能保留错误的最小反例。修复后把该反例保留下来，而不是只保留随机测试。

不要让参照实现复用同一个可能出错的离散化、边界计算或状态转移。例如验证前缀和代码时，暴力版应直接加原数组，而不是再次调用同一个前缀和查询函数。对拍也不能替代正确性证明：它擅长找反例，但有限输入全部通过不代表所有输入都正确。

### 检查不变量，比只检查返回值更早发现问题

- 差分：没有更新时，求前缀和应还原输入；累计多次更新后与逐元素修改一致。
- 单调队列：下标递增、对应状态值单调、队首没有过期；每次弹出都应有明确的淘汰理由。
- LFU：每个 key 恰在一个频次桶中，所有桶非空，桶数量不超过驻留 key 数。容量为 1 的长 get 序列能暴露“答案正确但内存增长”的问题。
- 路径恢复：首尾正确、每条边确实存在、总权重等于最短距离，前驱链不能成环。只比较距离不足以验证路径。

## 用假时钟测试限流

不靠 sleep 等待边界，而把时钟作为依赖传入，手动推进纳秒时间。这样测试快、可重复，也不会受机器负载影响。

窗口统一定义为 `(now-W,now]`，限额 2 次/1000ms：

| 请求时刻（ms） | 精确日志 | 保守子桶（100ms 桶宽） | 检查意义 |
|----------------|----------|-----------------------|----------|
| 1000 | 接收 | 接收 | 第一条请求 |
| 1099 | 接收 | 接收 | 额度用完 |
| 2000 | 接收 | 拒绝 | 1000ms 请求恰好过期；子桶可能保守多算 |
| 2001 | 拒绝 | 拒绝 | 1099ms 请求仍在精确窗口中 |

两种实现的承诺不同，不能强行要求返回值完全相同。精确日志与逐条时间历史一致；保守子桶可以误拒绝，但任何放行都不能突破真实滚动窗口上限。整形器另测 FIFO、队列容量和相邻出队间隔，不能用“准入返回了 true”替代出队验证。

## 本仓库的可执行检查

仓库提供 `npm run docs:check:algorithms`：直接提取相关文档的 Java 代码块，补上导入与测试外壳，在临时目录编译运行，结束后清理生成文件，不维护另一份算法实现。

需要先安装项目 Node 依赖，并准备 JDK 17 或更新版本。通过 `JAVA_HOME`、PATH 或参数指定 JDK：

```bash
npm run docs:check:algorithms
npm run docs:check:algorithms -- --java-home "C:/path/to/jdk"
```

检查覆盖选定的核心示例，不是所有 Java 代码块的编译承诺；带伪代码占位、题目上下文或外部库的示例需要另行验证。`npm run docs:check` 负责站点构建和生成页面链接，不能代替算法行为测试。
