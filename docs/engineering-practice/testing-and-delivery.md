# 测试策略与可靠交付

测试不是给实现补一张“覆盖率合格”的证明，而是把业务约束、失败假设和发布风险变成可重复验证的行为。面试中应能解释：**这项风险在哪一层测试最便宜、测试如何失败、通过后还剩什么不确定性**。

## 一、先按风险选测试层

| 测试层 | 主要验证 | 不能替代 |
|--------|----------|----------|
| 单元测试 | 纯业务规则、算法、状态转换、错误分类 | 数据库锁语义、真实协议和配置 |
| 集成测试 | 数据库事务、序列化、消息协议、迁移和框架边界 | 所有跨服务业务流程 |
| 契约测试 | 提供方与消费方对字段、状态码、错误和兼容性的约定 | 服务真正可用、权限正确、跨服务事务正确 |
| 端到端测试 | 少量关键用户路径、鉴权与部署组合 | 所有边界输入和并发时序 |
| 性能/容量测试 | 给定负载下的吞吐、尾延迟、资源与瓶颈 | 任意生产负载的永久容量保证 |
| 故障与恢复测试 | 超时、重试、主从切换、补偿、备份恢复 | 未覆盖故障的可靠性承诺 |

测试金字塔表达的是反馈成本与覆盖职责，不是固定的 `70/20/10` 配比。一个主要负责 SQL 并发裁决的服务，需要更多真实数据库测试；纯算法库则可以主要依赖单元、性质和差分测试。

### Mock、Stub 与 Fake

- Stub 提供预设响应，适合控制依赖返回的成功、失败和边界数据。
- Mock 常用于验证交互，但“调用了 repository.save”不证明事务已提交或唯一约束生效。
- Fake 是简化实现，例如内存仓储；它必须符合需要测试的契约，不能把普通 Map 当作数据库隔离级别的替身。

不要逐行镜像内部实现写测试，否则小重构就需要改一整套断言。优先断言外部结果、不变量和必要副作用，对调用次数的断言限于真正的契约，例如重复支付请求只产生一次扣款。

## 二、把业务不变量变成验收用例

以下是下单 API 的最小风险表，不绑定具体框架：

| 场景 | 必须保持的行为 | 观察点 |
|------|----------------|--------|
| 正常下单 | 正确订单、正确库存、可查询结果 | 持久化终态，不只检查 HTTP 200 |
| 相同幂等键并发提交 | 业务效果最多一次，可重放同一结果 | 唯一约束、订单数量、库存净变化 |
| 相同键不同参数 | 明确冲突，不能返回别人的结果 | 请求摘要、租户与身份作用域 |
| 提交成功但响应丢失 | 同键重试查询到已提交结果 | 客户端结果未知场景 |
| DB 回滚 | 订单、库存和同事务 Outbox 一起回滚 | 独立连接读取 |
| 发布消息后 ACK 丢失 | 重投不重复执行业务 | 持久去重与业务同事务 |
| 支付与超时关闭竞争 | 只允许合法状态转移，必要时进入退款协议 | 订单版本、外部支付流水、补偿记录 |

先说清“最多一次效果”和“最终完成”分别由什么保障。只做到拒绝重复请求，可能同时把一次合法失败重试也拒绝掉；只做到一直重试，则可能重复副作用。

## 三、确定性并发测试

### 不要用 sleep 猜测线程已经走到哪里

用 barrier、latch、可控制的 Promise/Future 或测试钩子暂停在关键点，再显式推进时序：

```text
测试线程启动请求 A
A 读取旧版本后停在 barrier
测试线程执行请求 B 并等待其提交新版本
释放 A，让它尝试回填或提交
断言：旧结果被拒绝，或系统按约定暴露冲突并重试
```

测试自身也要有超时和清理，避免一个失败让整个 CI 永久挂住。使用框架同步原语建立 happens-before，不用轮询普通变量伪造同步。

### 时间、随机数与外部依赖可控制

业务时间通过 Clock/时间源注入，超时与 TTL 用 fake clock 推进；真实网络和数据库仍要有独立的集成测试。随机测试固定 seed，失败时输出输入与 seed，再将最小反例变成固定回归测试。

对异步 UI，把 A 请求的响应延后，先完成 B，再放行 A；对消息消费者，把“事务提交”和“ACK”之间作为可注入失败点。验证的重点是危险交错，不是“同时开 100 个线程运行一次没出错”。

### 性质测试、差分测试与变异测试

| 方法 | 用途 | 风险 |
|------|------|------|
| 性质测试 | 对一类输入验证不变量，如库存不为负、排序后有序且元素多重集不变 | 性质太弱会让错误实现也通过 |
| 差分测试 | 与小规模暴力解或独立实现比对 | 两套实现共享同一错误假设 |
| 变异测试 | 故意改变比较符、删除分支，检验断言能否捕获 | 计算成本与等价变异需要管理 |

算法实例见 [一般流程](../data-structures-and-algorithms/foundations/problem-solving-workflow)，事务实例见 [事务管理](../web-and-frameworks/data-access/transaction)。

## 四、真实依赖与 Testcontainers

Testcontainers 可以在支持容器运行时的开发/CI 环境启动临时数据库、缓存或消息服务。它的价值是可重复的依赖环境，不是“用了容器就等价于生产”。

1. 使用与生产兼容的引擎、主要版本、字符集、时区和迁移脚本；H2 不自动等价于 MySQL，内存 Redis fake 不自动等价于 Cluster。
2. 等待真实 readiness，而不是仅等端口打开；使用独立 schema、数据库或唯一测试命名空间，保证可并行运行。
3. 事务测试应真实提交并用另一连接读取，覆盖 flush/commit 才出现的约束错误。
4. 测试结束清理资源；保留失败日志，但脱敏凭据与业务数据。CI 不应把高权限容器运行时无条件暴露给不可信 PR。
5. 不把一次单节点容器测试称为容灾测试；复制延迟、故障转移与跨节点路由需要对应拓扑。

## 五、API 与事件兼容性

“新增一个可选字段”通常比删除字段温和，但仍要验证消费端是否严格拒绝未知字段。更隐蔽的破坏包括：字段由可空改非空、默认值变化、枚举新增后旧代码无兜底、分页排序变化、时间单位由秒变毫秒。

发布提供方前运行消费者契约，发布消费者前验证旧提供方仍满足要求；有滚动升级时至少覆盖旧客户端/新服务端和新客户端/旧服务端的兼容窗口。消息还要考虑历史重放，而不只是在线实例的版本。

OpenAPI/Protobuf schema diff 能发现一部分结构问题，但不能发现“金额字段含义变化”等语义变化。保留黄金请求/响应、错误契约与业务场景回归；不要为了通过测试而自动接受所有新快照。

## 六、从 CI 绿灯到可靠发布

```text
静态检查、类型检查、密钥扫描
  -> 快速单元与性质测试
  -> 数据库/消息集成测试、兼容性检查
  -> 构建不可变制品，记录源码版本与依赖
  -> 漏洞/许可证/SBOM 与来源策略
  -> 关键端到端路径与迁移演练
  -> 灰度发布，观察 SLI 和停止条件
  -> 推广或回退，保留审计证据
```

**同一份制品逐级晋升**：测试过的镜像 digest 推到预生产和生产，不在每个环境重新构建一遍却沿用同一版本名。环境差异通过受控配置注入，敏感配置不放入镜像层。镜像来源、签名与密钥边界见 [Docker 容器化](./docker)。

**数据库迁移**使用 expand-contract：先加兼容结构，兼容读写并回填核对，再删除旧结构。旧应用回滚时要能读取新数据；不可逆迁移不能用一句“一键回滚”覆盖。

**灰度验收**既看技术错误率/P99，也看订单成功率、异步任务年龄、资金差异等业务指标。低流量灰度可能没有足够样本，必要时运行合成交易，但避免制造真实扣款或污染统计。

## 七、质量指标与不稳定测试

| 指标 | 能说明什么 | 不能说明什么 |
|------|------------|--------------|
| 行/分支覆盖率 | 哪些代码被测试执行过 | 断言是否有效、所有并发时序是否正确 |
| 失败率与 flake rate | 测试反馈是否可信 | 被重试抹掉的真实生产缺陷不存在 |
| 缺陷逃逸 | 哪些缺陷未在发布前发现 | 只凭短窗口零缺陷就证明质量完美 |
| 发布失败率/恢复时间 | 交付与恢复过程的表现 | 脱离变更规模与业务风险比较团队优劣 |

遇到 flaky test：先固定 seed、时间和资源，找共享状态、异步等待或顺序依赖；临时隔离需要负责人、原因和恢复期限。增加重试次数可以收集证据，但不应让“第 3 次才绿”自动成为合格门禁。

## 八、面试回答与练习

**问：覆盖率 90%，为什么还能出严重事故？** 覆盖率只证明执行过，不证明断言有力。可能没测试真实提交、重复投递、权限范围或线上配置组合。应从事故不变量反推最便宜的回归层，再补真实依赖或故障测试。

**问：上线前不可能穷尽所有情况怎么办？** 按影响和概率分层验证，记录未验证假设，用兼容发布、灰度、监控、回退和对账降低残余风险，而不是宣称测试足以保证零缺陷。

**练习**：为一个带幂等键的下单接口列出 8 个用例，标明测试层、控制的失败点、断言和外部依赖。至少包含并发重复、提交后断线、旧版本客户端、权限撤销与补偿重复；再说明哪些风险仍需预生产或生产小范围演练。
