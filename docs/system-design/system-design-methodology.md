# 系统设计方法论

## 概念

系统设计面试考察候选人从零开始设计一个大规模分布式系统的能力。面试官关注的不仅仅是最终答案，更重要的是**思考过程**：你如何分解问题、如何权衡取舍、如何在约束条件下做出合理决策。

与算法题不同，系统设计没有唯一正确答案。面试官希望看到：
- 结构化的思维方式
- 对分布式系统核心概念的掌握
- 主动识别瓶颈并提出优化方案的能力
- 清晰表达技术决策的沟通能力

## 核心原理

### 系统设计面试的标准步骤

#### 第一步：需求澄清（约 5 分钟）

在动笔之前，先把问题搞清楚。一个模糊的题目背后可能隐藏着截然不同的设计方向。

**功能需求（Functional Requirements）**
- 系统需要支持哪些核心功能？
- 用户能做什么操作？
- 哪些功能是 MVP，哪些是 Nice-to-have？

**非功能需求（Non-Functional Requirements）**
- 用户量级：DAU（日活）是多少？峰值流量是平时的几倍？
- 读写比：读多还是写多？（如微博 timeline 读写比可达 100:1）
- 数据量：系统需要存储多少数据？数据增长速度如何？
- 延迟要求：P99 延迟需要控制在多少毫秒以内？
- 可用性要求：需要几个 9（99.9% vs 99.99%）？
- 一致性要求：能否接受最终一致性？

> 面试技巧：不要假设，要询问。主动提问体现了你的工程经验，面试官希望看到这一点。

**需求澄清提问模板**

面试中可以直接套用的提问清单，根据题目类型选择相关问题：

```mermaid
flowchart LR
    subgraph 功能维度
    F1[核心用例是什么？]
    F2[用户角色有哪些？]
    F3[MVP 包含哪些功能？]
    F4[需要支持哪些端？<br/>Web/iOS/Android]
    end
    
    subgraph 规模维度
    S1[DAU/MAU 预期？]
    S2[读写比大约多少？]
    S3[数据保留多久？]
    S4[峰值是日常的几倍？]
    end
    
    subgraph 质量维度
    Q1[延迟目标？P99 < ?ms]
    Q2[可用性目标？几个9？]
    Q3[一致性要求？<br/>强一致 vs 最终一致]
    Q4[安全/合规约束？]
    end
```

**不同题型的关键提问**

| 题目类型 | 必须问的关键问题 | 为什么重要 |
|----------|-----------------|-----------|
| 存储类（短链、KV Store） | 数据量级？读写比？需要持久化吗？ | 决定是用 Redis 还是 MySQL，是否需要分库分表 |
| 社交类（Feed、IM） | 关系链密度？大 V 比例？群聊上限？ | 决定推拉模型选择和 Fan-out 策略 |
| 计算类（搜索、推荐） | 候选集规模？延迟容忍？需要实时更新吗？ | 决定召回策略和模型复杂度 |
| 实时类（监控、支付） | 数据到达延迟容忍？精确度要求？ | 决定是流式还是批处理 |

**常见陷阱**

::: warning 需求阶段常见错误
1. **直接开画架构图**：没搞清需求就开始设计，后面推翻重来浪费时间
2. **功能贪多**：试图在 45 分钟内设计一个完整的系统，应聚焦 2-3 个核心功能
3. **忽略非功能需求**：只考虑"能不能做"，不考虑"能做多大"，面试官会追问你没准备好的规模问题
4. **不与面试官互动**：单向输出 10 分钟没有一个问题，面试官认为你缺乏协作能力
:::

#### 第二步：容量估算（约 5 分钟）

用数字说话，帮助确定系统规模，指导后续的架构决策。

**QPS 估算公式**

$$\text{QPS} = \frac{\text{DAU} \times \text{每用户日均操作次数}}{86400}$$

以设计 Twitter 为例：
- DAU = 1 亿
- 每用户每天平均读 Timeline 20 次，发推 1 次
- 读 QPS = 100,000,000 × 20 / 86,400 ≈ **23,000 QPS**
- 写 QPS = 100,000,000 × 1 / 86,400 ≈ **1,200 QPS**
- 峰值倍数应从活动、时区和历史流量推导；缺少数据时可先假设 **3 倍**，再用 **10 倍**做敏感性分析，不把经验倍数当作事实。

**存储估算**

$$\text{日存储增量} = \text{写 QPS} \times 86400 \times \text{单条数据大小}$$

以 Twitter 为例：
- 每条推文约 300 bytes（文本） + 平均 10% 附带图片
- 纯文本日增量 = 1,200 × 86,400 × 300 bytes ≈ **31 GB/day**
- 5 年总存储 ≈ 31 GB × 365 × 5 ≈ **56 TB**

**带宽估算**

$$\text{出口带宽} = \text{读 QPS} \times \text{平均响应大小}$$

常用单位换算：
- 1 KB = 1,000 bytes
- 1 MB = 1,000 KB
- 1 TB = 1,000 GB
- 1 billion = 10 亿

> 估算不需要精确，数量级正确即可。重要的是展示你的思考逻辑。

#### 把估算推进到架构决策，而不只算出 QPS

**贯穿例子：商品详情 API**。题设为 1000 万 DAU、每人每天访问 20 次、峰值系数 8，单次响应 20KB；这些是用于讨论的假设，不是某家公司实际指标。

| 推导 | 结果 | 架构含义 |
|------|------|----------|
| 平均请求率 `1000万 × 20 / 86400` | 约 2315 QPS | 不能直接作为峰值容量 |
| 峰值请求率 `2315 × 8` | 约 18520 QPS | 后续用约 2 万 QPS 设计 |
| 出口 `20000 × 20KB` | 约 400MB/s，即 3.2Gbps | 还没算协议、复制和重试流量；评估 CDN、压缩与带宽 |
| 每请求串行执行 3 次 SQL，缓存未命中率 5% | `20000 × 5% × 3 = 3000` SQL/s | 应分别估计缓存命中与回源查询成本 |
| Redis 故障后无保护回源 | `20000 × 3 = 60000` SQL/s | 正常负载的 20 倍；必须设计回源预算和降级 |

**请求数不是工作量**：一次 Feed 读取扇出到 20 个分片，或一条发帖向 1000 个收件箱写入，都不能把外部 QPS 直接当作存储 QPS。估算应逐层记录“到达率 × 放大倍数 × 未被缓存/合并的比例”。

#### 并发、利用率和尾延迟

稳定系统中，Little 定律给出平均在途请求数：

$$
L = \lambda W
$$

若请求率 2 万/s、平均停留时间 50ms，平均在途约 1000。若依赖变慢到 500ms，在相同到达率且仍可稳定处理的假设下会需要约 10000 个在途位置；实际池容量不够时则表现为排队、拒绝或超时。**不能用 P99 直接代替平均值套公式，也不能在已经失稳的系统中把它当容量保证。**

假设压测得到：固定请求混合和数据规模下，每实例在目标 P99 内的安全容量为 2000 QPS。2 万 QPS 至少需要 10 个实例，但还没考虑故障域。如果均匀分布在三个 AZ，并要求任一 AZ 故障后仍承受全量流量，则：

$$
N_{total} \geq \left\lceil \frac{Q_{peak}}{C_{safe}(1-f)} \right\rceil
$$

其中 $f=1/3$ 是最大故障域损失比例，得到至少 15 个实例；还需检验流量倾斜、滚动发布、冷启动和下游容量。这里的 `C_safe` 已含目标延迟下的余量，不再重复机械乘一次“利用率 70%”。

并行依赖也会放大尾延迟：若 20 个相互独立的依赖各有 1% 概率超时，至少一个超时的概率为 `1 - 0.99^20 ≈ 18.2%`。真实依赖可能相关，因此还需 trace 与故障数据验证；不能把各组件 P99 简单相加当成请求 P99。

#### 存储估算还缺哪几项？

把“裸业务数据”与“实际资源”分开：主数据 + 索引 + 副本 + 事务/复制日志 + 历史版本 + 备份 + 扩容迁移临时空间。压缩率、删除回收时机和热数据比例都要显式假设。缓存只覆盖工作集，不能用总历史数据量直接决定内存；热点分布则决定某个分片是否先被打满。

最后回答三个问题：**哪个假设最不确定、它翻倍会先压垮哪里、上线后用什么指标验证？** 这比背某个产品“单机固定多少 QPS”更有说服力。

#### 第三步：高层设计（约 10 分钟）

画出核心组件和数据流。用 ASCII 图或白板快速勾勒架构全貌。

**标准组件清单**

| 组件 | 缩写 | 作用 |
|------|------|------|
| 客户端 | Client | 浏览器、移动端 App |
| 负载均衡 | LB | 流量分发，健康检查 |
| API 网关 | API GW | 鉴权、限流、路由 |
| 应用服务 | Service | 业务逻辑处理 |
| 数据库 | DB | 持久化存储 |
| 缓存 | Cache | 降低延迟，减少 DB 压力 |
| 消息队列 | MQ | 异步解耦，削峰填谷 |
| CDN | CDN | 静态资源加速 |
| 对象存储 | OSS | 图片、视频等大文件 |

**组件选型决策指南**

面试中需要快速判断架构中应该引入哪些组件。以下是通用决策流程：

```mermaid
flowchart TD
    A[收到设计题] --> B{读多还是写多？}
    B -->|读多写少| C[评估热点与陈旧容忍度<br/>决定是否引入缓存]
    B -->|写多读少| D[先明确写入确认语义<br/>再考虑队列与批处理]
    B -->|读写均衡| E[优先优化数据库<br/>索引 / 读写分离]
    
    A --> F{是否有大文件？<br/>图片/视频/文档}
    F -->|是| G[对象存储 + CDN]
    F -->|否| H[不需要 OSS]
    
    A --> I{是否有实时通信？<br/>聊天/通知/协作}
    I -->|是| J[WebSocket / SSE]
    I -->|否| K[普通 HTTP API<br/>需要更新时再评估轮询]
    
    A --> L{是否有搜索需求？<br/>全文检索/模糊匹配}
    L -->|是| M[按检索规模评估<br/>数据库全文索引或搜索引擎]
    L -->|否| N[按访问模式设计<br/>数据库索引]
    
    A --> O{是否需要定时/延迟任务？}
    O -->|是| P[延迟队列 / 定时调度]
```

**组件引入原则**：不要为了展示知识面而堆砌组件。每引入一个组件都要说出**为什么需要它**以及它解决的**具体瓶颈**。面试官更看重你对每个组件职责的深刻理解，而非数量。

#### 第四步：详细设计（约 15 分钟）

深入核心模块，展示你对技术细节的掌握。

**数据库 Schema 设计**
- 明确主键和索引策略
- 考虑数据访问模式（按用户 ID 查、按时间排序等）
- 关系型 vs NoSQL 的选型理由

**API 设计（RESTful 风格）**

```
POST   /api/v1/links          # 创建短链
GET    /api/v1/links/{code}   # 获取原始链接（内部）
GET    /{code}                # 重定向（对外）
DELETE /api/v1/links/{code}   # 删除短链
GET    /api/v1/links/{code}/stats  # 查看统计
```

**核心算法与数据结构选择**
- 用 Redis Sorted Set 实现排行榜
- 用 Bloom Filter 快速判断数据是否存在
- 用一致性哈希（Consistent Hashing）实现分布式缓存节点分配

**数据建模思维框架**

面试中设计数据库 Schema 时，按以下步骤思考：

```mermaid
flowchart TD
    A[确定核心实体] --> B[识别实体间关系<br/>1:1 / 1:N / M:N]
    B --> C[确定访问模式<br/>主要查什么？怎么查？]
    C --> D{访问模式匹配哪种存储？}
    D -->|强关系 + 事务| E[MySQL / PostgreSQL<br/>范式化设计]
    D -->|灵活嵌套 + 频繁变更| F[MongoDB<br/>反范式化设计]
    D -->|高写入 + 时序| G[Cassandra / HBase<br/>宽表设计]
    D -->|缓存 + 计数| H[Redis<br/>选择合适数据结构]
    
    E --> I[设计主键和索引]
    I --> J[考虑分片策略]
    J --> K[评估数据量增长]
```

**常见数据建模决策**

| 决策点 | 选项 A | 选项 B | 判断依据 |
|--------|--------|--------|----------|
| 范式化 vs 反范式化 | 第三范式（无冗余） | 冗余存储（空间换时间） | 读多用反范式减少 JOIN；写多用范式减少更新量 |
| 自增 ID vs UUID | 自增（有序、紧凑） | UUID / Snowflake 等 | 按唯一性作用域、索引局部性、生成器可用性和可预测性选择；号段也是选项 |
| 软删除 vs 硬删除 | `is_deleted` 标记 | 直接 DELETE | 需要审计/恢复用软删；简单场景用硬删 |
| 单表 vs 多表 | 所有字段一张表 | 拆分（基本信息 + 扩展信息） | 根据访问频率、行宽、更新热点和事务边界，不按固定字段数机械拆表 |

**API 设计深入**

```
RESTful 核心原则：
1. 资源用名词复数：/api/v1/users（不是 /getUser）
2. HTTP 动词表示操作：GET 读 / POST 创建 / PUT 全量更新 / PATCH 部分更新 / DELETE 删除
3. 状态码表达语义：200 成功 / 201 已创建 / 400 参数错误 / 404 不存在 / 429 限流 / 500 内部错误
4. 分页用 cursor 优于 offset：offset 大页码性能差，cursor 基于上一页最后一条记录 ID
5. 版本管理：URL 路径（/v1/）比 Header 更直观，面试中优先选这种
```

**幂等性设计**

在面试中提及 API 幂等性是加分项：

| HTTP 方法 | 天然幂等？ | 需要额外处理？ |
|-----------|-----------|--------------|
| GET | 是 | 不需要 |
| PUT | 语义要求幂等 | 实现仍需避免重复副作用；并发覆盖可配合 ETag/If-Match |
| DELETE | 语义要求幂等 | 重复响应状态码可以不同，仍需保证业务效果不会重复 |
| POST | 否 | **需要**：通过幂等 key（`Idempotency-Key` Header）防重 |

```
POST /api/v1/orders
Header: Idempotency-Key: uuid-abc-123
Body: { "itemId": 1001, "quantity": 1 }

服务端逻辑：
1. 在身份/租户范围内校验 key，计算规范化请求摘要
2. 依靠数据库唯一约束竞争同一 key，不是先 GET 再决定创建
3. 同一事务写入订单、幂等记录及需要发布的 Outbox 事件
4. 已完成的相同请求重放结果；相同 key 不同摘要返回冲突
5. 超时结果未知时，用同一 key 查询或重试，不能换 key 再创建
```

Redis 可以加速结果查询，但不能代替订单数据库的唯一约束。去重记录保留时间应覆盖客户端重试和事件回放范围；“24 小时”不是所有业务通用答案。状态机与结果重放详见 [幂等性与热点 Key 设计](./hot-key-and-idempotency)。

#### 先声明业务不变量，再画失败路径

对下单场景，不变量可以是“可售库存不为负”“同一业务请求只产生一个订单”“同一订单最多确认一次扣款”。随后为每一步声明提交点、可见性和恢复者：

| 问题 | 一个可审查的回答 |
|------|------------------|
| `201` 或 `202` 到底承诺什么？ | `201` 表示订单已按约定持久化；`202` 表示任务已可靠受理，仍可能业务失败 |
| 请求超时能否判失败？ | 不能，可能已提交但响应丢失；查询同一 requestId 的结果 |
| DB 成功、发消息失败怎么办？ | 业务变更与 Outbox 同事务，派发器至少一次重试 |
| 下游副作用不能回滚怎么办？ | 用状态机、补偿动作及对账；补偿不是把现实中的副作用“撤销到未发生” |
| 用户刚写完就读到旧值怎么办？ | 在规定范围内读主、携带版本下界或等待复制追上，而不是只说“最终一致” |
| 哪些失败允许降级？ | 商品推荐可省略；实际成交价格、权限与扣款不能悄悄使用过期兜底值 |

一致性应按操作说明：读己之写、单调读、唯一性、事务隔离、线性一致性不是同义词，也不需要给整个系统只贴一个“强一致”标签。

#### 第五步：扩展与优化（约 10 分钟）

识别系统瓶颈，提出可落地的优化方案。

**水平扩展（Scale Out）**
- 应用层：无状态设计，Session 外置到 Redis
- 数据层：数据库分片（Sharding），按用户 ID 取模

**缓存策略**
- Cache-Aside（旁路缓存）：最常用，先查 Cache，Miss 则查 DB 并回填
- Write-Through：通过统一写路径更新底层存储与缓存；一致性还取决于并发控制、失败恢复及是否存在旁路写入
- Cache 失效策略：TTL + LRU 淘汰

**数据库优化**
- 读写分离：写 Primary，读 Replica，适合读多写少场景
- 分库分表：按业务分库，按数据量分表，注意跨分片查询问题

**异步化**
- 非关键路径操作（发通知、更新统计）移入消息队列
- 削峰填谷：应对流量突刺，保护下游服务

**瓶颈分析方法论**

面试中系统设计的加分项之一是**主动识别瓶颈**。以下是系统化的分析思路：

```mermaid
flowchart TD
    A[识别瓶颈] --> B{哪一层是瓶颈？}
    B -->|接入层| C[文件描述符与连接内存<br/>端口与连接跟踪资源]
    B -->|计算层| D[CPU/内存瓶颈<br/>单实例 QPS 上限]
    B -->|存储层| E[磁盘 IOPS / 网络带宽<br/>数据库连接池]
    B -->|网络层| F[带宽 / 延迟<br/>跨机房 RTT]
    
    C --> G[解决：LB + 多实例水平扩展]
    D --> H[解决：无状态设计 + 自动扩缩容]
    E --> I[解决：缓存 + 读写分离 + 分片]
    F --> J[解决：CDN + 压缩 + 多地域部署]
```

**经典系统各层吞吐量参考值**

下表只能作为假设讨论的量级例子，不是产品上限，也不应直接用于预算。硬件、请求复杂度、记录大小、持久化和一致性配置均会改变结果：

| 组件 | 单实例吞吐参考 | 瓶颈在哪 |
|------|---------------|---------|
| Nginx（反向代理） | 10K~50K QPS | 连接数、CPU |
| Spring Boot 应用 | 1K~5K QPS | CPU、线程池 |
| MySQL（单机） | 3K~8K QPS（混合读写） | 磁盘 IOPS、锁竞争 |
| Redis（单机） | 50K~100K QPS | 内存、网络带宽 |
| Kafka（单分区） | 10K~100K msg/s | 磁盘顺序写 |
| Elasticsearch | 5K~20K QPS（搜索） | 内存、CPU |

> 更好的表述是“在给定硬件、索引、读写混合和数据量下，先假设数据库安全容量为 5000 QPS，后续以目标 P99 的压测确认”。还要记录 CPU、IOPS、锁等待、连接池和副本延迟，知道容量先被什么限制。

#### 第六步：权衡讨论

系统设计没有银弹，所有选择都是权衡。主动讨论取舍展示了你的成熟度。

| 维度 | 选项 A | 选项 B | 如何权衡 |
|------|--------|--------|---------|
| 分区时的一致性 vs 可用性 | 拒绝无法确认的操作 | 接受部分操作并承担冲突处理 | CAP 讨论网络分区条件下的取舍，不能等同于日常业务 SLA |
| 性能 vs 成本 | 全量缓存 | 按需缓存 | 热数据比例、内存成本 |
| 简单 vs 灵活 | 单体架构 | 微服务 | 团队规模、业务复杂度 |
| 延迟 vs 吞吐 | 同步处理 | 异步处理 | 用户体验要求、数据实时性要求 |

**更多权衡维度**

| 维度 | 选项 A | 选项 B | 判断依据 |
|------|--------|--------|----------|
| SQL vs NoSQL | 关系型数据库 | 文档/列族/KV | 数据模型、一致性需求、扩展方式 |
| 推模型 vs 拉模型 | 写时扩散 | 读时聚合 | 读写比、Fan-out 规模、延迟容忍 |
| 长连接 vs 短连接 | WebSocket / gRPC 流 | HTTP 轮询 | 实时性要求、客户端数量 |
| 集中式 vs 去中心化 | 单点协调器 | 事件驱动 / P2P | 故障域、延迟、可观测性 |
| 预计算 vs 实时计算 | 离线预生成结果 | 在线实时计算 | 数据新鲜度要求、计算成本 |

**权衡讨论的面试话术**

面试中讨论权衡时，建议用以下句式展示思考深度：

> "我选择方案 A 而不是方案 B，是因为在当前场景下 [具体约束]。如果 [条件变化]，我会考虑切换到方案 B。"

示例：
> "我选择 Redis 缓存而不是本地缓存，是因为这是多实例部署，需要所有实例共享同一份缓存数据。如果是单实例部署或者热点数据需要微秒级访问，我会加一层 Caffeine 本地缓存。"

这种**条件化表述**比单纯选 A 或选 B 更显深度，面试官会认为你有工程经验而非纸上谈兵。

### 完整案例走读：设计一个短链接系统

#### 需求澄清

**功能需求**
- 输入长 URL，生成唯一短链（如 `https://short.ly/abc123`）
- 访问短链，301/302 重定向到原始 URL
- 支持自定义短码（可选）
- 统计每条短链的点击次数

**非功能需求**
- 高可用：99.99%（短链失效影响业务）
- 低延迟：重定向 P99 < 10ms
- 短码不可预测（安全考虑）
- 短链有效期支持设置

#### 容量估算

```
写操作：1 亿条短链 / 月 = 100M / (30 × 86400) ≈ 40 写/秒
读操作：读写比 100:1 → 4,000 读/秒（峰值 ~40,000 读/秒）

存储：
  每条记录约 500 bytes（短码 + 原始 URL + 元数据）
  10 年数据量 = 100M × 12 × 10 × 500 bytes ≈ 6 TB
```

#### 高层设计

```
用户
  │
  ├── 创建短链 ──► API Service ──► DB (写)
  │                    │
  │                    └──► ID Generator (短码生成)
  │
  └── 访问短链 ──► Redirect Service
                       │
                       ├──► Cache (Redis) ──► 命中则直接返回
                       │
                       └──► DB (读) ──► 回填 Cache
                                │
                                └──► 异步更新点击统计 (MQ → Worker)
```

#### 短链生成算法

**方案一：Base62 编码 + 自增 ID**

```
自增 ID（如 12345678）→ Base62 编码 → "dnh75"（6位可表示 62^6 ≈ 568 亿条）

Base62 字符集：0-9, a-z, A-Z
优点：简单，无冲突
缺点：短码连续可预测，需要分布式 ID 生成器（如 Snowflake）
```

**方案二：哈希 + 冲突处理**

```
MD5(原始 URL) → 取前 6 位 → 检查 DB 是否冲突
若冲突 → 追加随机盐重新哈希

优点：相同 URL 可生成相同短码（去重）
缺点：冲突检查需要 DB 查询，高并发下压力大
```

推荐方案需要跟需求一致：若短码必须难以猜测，可使用**安全随机数生成 10 位 Base62 短码 + 数据库唯一约束 + 有限冲突重试**；Snowflake + Base62 适合可接受可预测性的场景，编码不是加密。64 位 ID 的 Base62 最长可能需要 11 位，不能固定按 6 位设计。

#### 数据库设计

```sql
CREATE TABLE short_links (
    id          BIGINT PRIMARY KEY,        -- Snowflake ID
    short_code  VARCHAR(12) CHARACTER SET ascii COLLATE ascii_bin UNIQUE NOT NULL,
    original_url TEXT NOT NULL,
    user_id     BIGINT,                    -- 创建者（可为空，匿名）
    expires_at  DATETIME,                  -- 过期时间（NULL 表示永久）
    created_at  DATETIME DEFAULT NOW(),
    click_count BIGINT DEFAULT 0           -- 近似统计，精确统计走独立表
);

CREATE INDEX idx_short_links_expiry ON short_links(expires_at);
```

点击统计使用独立表，避免高频更新锁住主表：

```sql
CREATE TABLE click_events (
    id         BIGINT PRIMARY KEY,
    short_code VARCHAR(12) CHARACTER SET ascii COLLATE ascii_bin,
    clicked_at DATETIME,
    ip         VARCHAR(45),
    user_agent TEXT,
    INDEX idx_click_events_time (clicked_at)
  );
```

  以上采用 MySQL 风格，Base62 必须区分大小写，避免数据库默认排序规则把 `a` 与 `A` 当作相同短码。`UNIQUE` 已建立索引，无需再建一份相同索引。点击事件是否分区应另按归档量评估；MySQL 分区表的唯一键必须包含分区列，不能给现有主键表随手追加一个不完整的分区子句。

#### 缓存策略

```
短链重定向是典型的读多写少场景，缓存命中率应 > 90%。

Key:   short_code（如 "abc123"）
Value: original_url
TTL:   与短链过期时间对齐，最长 24 小时

缓存穿透防护：对不存在的短码缓存空值（TTL 60s）
缓存击穿防护：热点短码加互斥锁，防止并发 DB 查询
```

#### 扩展考虑

| 瓶颈 | 解决方案 |
|------|---------|
| 单点 Redis | Redis Cluster，按 short_code 分片 |
| 单 DB 写瓶颈 | 按 short_code 前缀分库（16 个分片） |
| 点击统计写压力 | 写入 Kafka，批量聚合后落库 |
| 全球访问延迟 | 多地域部署 + GeoDNS 就近路由 |
| 短码生成单点 | 多实例 Snowflake，机器 ID 不同 |

#### 深入思考：边界情况

**短码冲突处理方案对比**

```mermaid
flowchart TD
    A[生成短码] --> B{使用哪种算法？}
    B -->|Snowflake + Base62| C[验证机器 ID 与时钟策略<br/>保证生成器唯一性]
    B -->|随机短码或哈希映射| D{唯一约束插入成功？}
    D -->|是| E[返回已持久化短链]
    D -->|否| F[生成新候选<br/>有限重试]
    F --> D
    
    C --> G[唯一约束仍作最后防线<br/>编码不提供不可预测性]
```

| 方案 | 冲突概率 | 性能 | 复杂度 | 适用场景 |
|------|----------|------|--------|----------|
| Snowflake + Base62 | 取决于生成器唯一性前提 | 本地生成快，写入仍需约束 | 中 | 可接受可预测性，正确管理机器 ID 与时钟 |
| 哈希映射到 N 位 Base62 | 随已占用空间增长 | 需处理唯一约束冲突 | 中 | 相同 URL 去重，还需明确租户和过期语义 |
| 自增 ID + Base62 | 依赖数据库序列唯一性 | 生成依赖数据库或号段服务 | 低 | 可接受短码可预测 |
| 安全随机 Base62 | 随已占用空间增长 | 有限重试，唯一约束裁决 | 低 | 需要难猜测的短码 |

若空间大小为 $S=62^N$，已有 $k$ 个不同短码，则下一次均匀随机候选碰撞概率约为 $k/S$；累计碰撞要考虑生日效应，不是始终 `1/S`。MD5 十六进制文本截取 6 位只有 $16^6$ 种，不等于 6 位 Base62。难猜测也不是访问授权，私有链接仍需鉴权。

**过期清理策略**

短链过期后按保留策略清理或归档，但通常**不要复用公开短码**：历史消息、浏览器和 CDN 可能仍持有链接，复用会把旧链接导向新资源。过期判断必须发生在访问路径，不能依赖定时清理准点运行。

```mermaid
sequenceDiagram
    participant Scheduler as 定时任务
    participant DB as MySQL
    participant Cache as Redis
    participant Archive as 归档存储
    
    Scheduler->>DB: 扫描 expires_at < NOW()<br/>批量查询（每次 1000 条）
    DB-->>Scheduler: 返回过期记录
    Scheduler->>Archive: 归档过期数据（可选）
    Scheduler->>DB: 提交过期标记与可靠失效事件
    Scheduler->>Cache: 提交后删除缓存，失败由事件重试
    
    Note over Scheduler: 每 5 分钟执行一次<br/>低峰期加大批次
```

**关键设计点：**
- 使用 `expires_at` 索引加速扫描，避免全表查询
- 批量处理（每次 1000 条），避免长事务锁表
- 缓存同时保存 `expires_at` 并在重定向前校验；数据库提交后可靠失效，防止清理期间重新回填旧值
- 低峰期（凌晨）执行大批量清理，高峰期减小批次

**多地域部署的一致性挑战**

全球化短链服务需要多地域部署以降低用户访问延迟：

```mermaid
graph TB
    subgraph 多地域短链架构
    GeoDNS[GeoDNS<br/>就近路由] --> US[美国节点<br/>Redis + DB 副本]
    GeoDNS --> EU[欧洲节点<br/>Redis + DB 副本]
    GeoDNS --> CN[中国节点<br/>Redis + DB 副本]
    
    CN -->|主库写入| Primary[(主库<br/>中国)]
    Primary -->|异步复制| US
    Primary -->|异步复制| EU
    end
```

**核心挑战与解决方案：**
- **短码唯一性**：所有写入集中在主库，或使用分段 Snowflake（不同地域使用不同机器 ID 段）
- **复制延迟**：若需要创建后立即访问，副本 miss 可受控回查权威主库或按写入地域路由；否则新短链可能被误缓存为“不存在”
- **缓存一致性**：各地域 Redis 独立缓存，通过 TTL 自然过期保持最终一致
- **就近读取**：命中时尽量在本地处理；P99 < 10ms 应明确是服务端处理时间还是用户端总延迟，跨地域 RTT 不能被省略

**Q2：设计一个短链接系统**

参考上方「完整案例走读」，回答要点：

1. **先澄清需求**：读写比、日活、是否需要自定义短码、统计维度
2. **给出估算**：100M URLs/月，读写比 100:1，峰值 4 万读 QPS
3. **架构分层**：写链路（API + ID生成 + DB）和读链路（重定向 + Cache + DB）分开讨论
4. **短码算法**：按不可预测性要求比较安全随机码与 Snowflake + Base62，以唯一约束处理冲突
5. **缓存是核心**：重定向路径上 Redis 缓存是降延迟的关键，Cache-Aside 模式
6. **主动提扩展**：分库分表、Kafka 异步统计、多地域部署

---

**Q3：如何估算系统的 QPS 和存储需求？**

**QPS 估算三步法**：

1. 确定 DAU（日活用户数）
2. 估算每用户每天的操作频率（读/写分别估算）
3. 套公式：$\text{QPS} = \frac{\text{DAU} \times \text{操作频率}}{86400}$，峰值系数作为明确假设，并评估活动突发、扇出与故障回源

**存储估算三步法**：

1. 确定写 QPS 和单条记录大小
2. 计算日增量：$\text{日增} = \text{写 QPS} \times 86400 \times \text{记录大小}$
3. 推算总量：日增 × 保留年限 × 副本数

**常用数量级记忆**：

| 数量 | 说明 |
|------|------|
| $10^3$ | 千，1 KB |
| $10^6$ | 百万，1 MB |
| $10^9$ | 十亿，1 GB |
| $10^{12}$ | 万亿，1 TB |
| 86,400 | 一天的秒数 |
| 2,592,000 | 一个月的秒数（30天） |

回答时要自信地报出具体数字，不要说"大概差不多"。数量级正确即可，过程清晰比结果精确更重要。
