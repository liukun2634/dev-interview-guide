# 高并发写架构 — 秒杀 / 抢单 / 发帖怎么扛

<span class="dig-tag dig-tag--category">系统设计</span> <span class="dig-tag dig-tag--hard">⭐⭐⭐ 进阶</span> <span class="dig-tag dig-tag--hot">🔥🔥🔥 必考</span>

::: tip 💡 核心要点
高并发写要同时回答三个问题：**哪些请求有资格进入、什么时候算可靠受理、最终业务不变量由谁维护**。限流减少无效工作，Redis 可以预筛选或暂时预留，MQ 吸收有界突发；它们不能代替权威数据库的条件更新、业务幂等和失败恢复。不要把“命令原子”直接推导成“订单不丢、库存不超卖”。
:::

## 这页解决什么问题

面试题：
- "**设计秒杀系统**" / "**双 11 库存扣减**" / "**春运抢票下单**"
- "**设计微博发帖**" / "**朋友圈发布**"
- "**设计支付下单**" / "**外卖下单 + 派单**"
- "**点赞 / 关注 / 收藏**这种轻写量怎么扛"

写流量的共同特征：
- **必须落库**（不能像读那样靠缓存命中跳过 DB）
- **强一致要求高**（订单不能丢、库存不能超卖）
- **写放大效应**（一条微博推给 1000 follower → 1 写 = 1000 推送）

**与读架构的关键差异**：

| 维度 | 读架构 | 写架构 |
|------|------|------|
| 缓存策略 | 多级缓存吃 99% 流量 | 缓存只能做"扣减预处理"，写还得落库 |
| 一致性 | 按业务确定陈旧容忍度 | 库存非负、唯一订单等不变量需原子维护；通知等可最终一致 |
| 削峰方式 | 缓存命中削峰 | **MQ 削峰** + 限流前置拦截 |
| 数据库压力 | 索引、缓存与副本分担 | 先定位锁、事务、索引和 I/O，再考虑分片 |
| 异步化 | 预计算、刷新也可能异步 | 由确认语义和等待时间决定，不是所有写都必须进 MQ |

## 全链路架构总览（秒杀场景）

下面以“短时 100 万次点击、仅 1000 件商品”为简化题设。用户数不等于 QPS，拦截比例与处理速率必须另行假设，不能当作现成压测结论。

```
                    100w 用户点击 "立即购买"
                            │
                            ▼
              ┌──────────────────────────┐
        ① CDN │  CDN: 秒杀按钮静态化      │  挡 0%（CDN 不挡写请求）
              │  + 验证码/答题前置降速    │  → 100w QPS
              └────────┬─────────────────┘
                       ▼
              ┌──────────────────────────┐
        ② GW  │  网关: 限流 + 黑名单     │  挡 90% → 剩 10w
              │  - 单用户 1 次/秒         │
              │  - 黄牛 IP 黑名单         │
              │  - 验证码失败拦截         │
              └────────┬─────────────────┘
                       ▼
              ┌──────────────────────────┐
        ③ APP │  应用层: Redis 预扣库存   │  挡 99% → 剩 1000
              │  Lua 条件预留 + requestId│
              │  失败的直接返回 "已售罄"   │
              └────────┬─────────────────┘
                       │ 1000 真正下单
                       ▼
              ┌──────────────────────────┐
        ④ MQ  │   消息队列削峰           │  写入 Kafka/RocketMQ
              │  返回用户 "排队中..."      │
              └────────┬─────────────────┘
                       ▼ 后台消费者按 DB 承载力慢慢写
              ┌──────────────────────────┐
        ⑤ DB  │   数据库: 落单           │  实际写入 1000 条订单
              │  分库分表（按 userId）    │
              └──────────────────────────┘
```

图只展示流量分层；真正返回“排队中”之前还必须完成可靠受理。下面采用**持久请求账本 + Outbox + MQ + 幂等消费者**细化这一步，不把短 TTL 的 Redis 预订单当作持久承诺。

## 每层方案与细节

### ① CDN — 把"秒杀按钮"挡在外面

写请求 CDN 没法直接缓存，但能做两件事：

**1. 秒杀页面静态化**：商品图、规则文案、按钮的 JS / CSS 全部静态化推 CDN，**减少回源压力**。

**2. 前置验证码 / 答题**（关键降速）：
- 用户点"立即购买" → 弹出验证码 / 数学题
- 答完才允许真正发起下单请求
- **削峰 + 防机器人** 一举两得

验证码是风险控制的一环，不保证固定削峰比例，也不是服务端授权。假设 100 万次请求能均匀摊到 30 秒，平均约 3.3 万次/s，但实际仍可能集中到达；服务端必须验证凭证、有效期和使用次数，不能只依赖前端按钮限制。

### ② API 网关 — 多维度限流挡 90%

写场景的网关比读场景更狠：

| 限流维度 | 阈值 | 目的 |
|------|------|------|
| **单用户** | 1 次/秒 | 防点击狂魔 |
| **单 IP** | 10 次/秒 | 防机房代理刷 |
| **单接口** | 总 QPS 限到 10w | 兜底保护 |
| **黑名单** | 历史黄牛 / 异常 IP | 风控前置 |

**面试加分点**：黑名单不光是限流，**风控系统**会做"账号特征评分"——新注册账号、设备指纹异常、有刷单历史 → 直接拒绝或限流到 0.1 次/秒。

### ③ 应用层 — Redis 预扣库存（**最关键**）

**核心思路**：Redis 只承担前置资格筛选/临时预留，权威库存和最终订单由持久化事务决定。不要用 `DECR -> 判断负数 -> INCR` 代替完整协议：后续补偿、重试、主从切换和预订单丢失都可能改变计数。

```text
POST /purchase-requests，携带稳定 Idempotency-Key
  1. 校验身份、限购、数量与活动状态，先查相同请求是否已有结果
  2. Redis 有界 Lua：检查剩余资格 + 记录 requestId + 条件预留
  3. 数据库短事务：插入持久请求账本 + Outbox；唯一约束裁决重复请求
  4. 提交成功才返回 202 与 requestId、结果查询地址
  5. Outbox 派发器投递 MQ，结果未知时以相同 eventId 重试
  6. 消费者事务：检查请求状态、条件扣权威库存、插入订单、写终态
  7. 查询接口返回 PROCESSING / SUCCEEDED / REJECTED，不无限“排队中”
```

**关键设计**：
- **Lua 的作用**：让同一 Redis 主节点上的检查、预留和请求去重不交错；相关 key 在 Cluster 下必须同 slot，脚本错误不会自动回滚。
- **持久受理成本**：步骤 3 仍要写数据库，必须为它做容量与限流预算。它避免了完整业务事务同步执行，但不让写入成本消失。更高规模可选持久日志作为受理源，同时另行设计查询与恢复索引。
- **`202` 的语义**：已可靠受理但未保证买到商品。Redis 资格因故障切换等失真时，最终 DB 仍可拒绝；接口必须允许终态为失败。
- **临时预留恢复**：未可靠受理的预留由扫描与超时协议释放；先查询账本确认不存在/已终止，再以 requestId 幂等释放，不能遇到网络异常就盲目 INCR。
- **失败重试**：响应丢失后用原 requestId 查询；同 key 不同请求摘要返回冲突，不能生成新 key 再扣一次。

如果业务要求“返回成功就已拿到库存”，应在返回前完成权威库存预留事务，然后异步完成后续工作，不能把前置 Redis 资格当作这个承诺。

### ④ MQ 削峰 — 同步转异步

**核心目的**：让数据库按自己节奏慢慢消费，**不被瞬时流量打垮**。

```
1000 QPS 预扣成功
   ↓
Kafka/RocketMQ 缓冲
   ↓
消费者按 200 QPS 写 DB（DB 极限的 50%，留 buffer）
   ↓
完成订单 → 状态通知用户（轮询 / WebSocket）
```

**MQ 选型**：

| 场景 | 推荐 |
|------|------|
| 秒杀 / 单 region | **RocketMQ**（事务消息成熟，金融场景多）|
| 日志 / 全球高吞吐 | **Kafka** |
| 简单业务 | **Redis Stream** |

**必须考虑的 3 个细节**：
1. **消息不丢**：MQ 持久化 + 消费 ACK + 失败重试
2. **幂等消费**：网络重试可能消费两次，用 `Idempotency-Key` 去重（详见 [幂等性](./hot-key-and-idempotency)）
3. **死信队列**：连续失败的消息进 DLQ，人工排查

#### 削峰不是无限排队：算出积压与恢复时间

设到达率为 $\lambda$，处理率为 $\mu$，单位为条/s；持续时间为 $t$，初始积压为 $B_0$：

$$
B(t) \approx \max(0, B_0 + (\lambda-\mu)t)
$$

假设 1000 条/s 持续 30 秒，消费者只能完成 200 条/s，新增积压约 `800 × 30 = 24000` 条。峰值结束后仍有 100 条/s 新流量，净消化能力只有 100 条/s，清空约需 240 秒，而不是 `24000 / 200 = 120` 秒。

若用户最多允许排队 30 秒，200 条/s 的处理能力对应的队列上限量级只有 6000 条，实际还要扣除处理和重试预算。超过阈值应拒绝新受理或进入明确的预约模式，不能无限返回 pending。

监控要同时包含**最老消息年龄、到达/处理速率、重试占比、终态完成率**。长度相同的队列可能对应完全不同的等待时间；处理能力不高于持续到达率时，仅扩队列容量永远无法恢复。

### ⑤ 数据库 — 分库分表防瓶颈

**先测瓶颈，不能背单库固定上限**：单行库存竞争、不同订单独立插入、大事务和多索引更新的吞吐完全不同，还受硬件、日志刷盘和复制配置影响。

假设题设压测表明单库可支撑目标负载，先保留简单架构。只有持续容量超出单机、访问局部性明确时，才讨论分片。以下只是容量规划示例，不保证吞吐线性叠加：

```
按 userId 取模分 16 库 × 16 表 = 256 物理表
假设每表计划保留约 500 万行

总容量：256 × 500w = 12.8 亿行
总写入能力：由最热分片、共享依赖和跨分片事务决定，需验证
```

**分库分表中间件**：ShardingSphere、TiDB、PolarDB-X（详见 [存储选型](./database-selection)）。

**热点行问题**：秒杀时所有人都在改一条库存记录（哪怕 Redis 挡掉了，DB 还是要写 1000 次同一行）。

**解法**：库存分桶
```sql
-- 原表
stock(item_id, count)  -- 单行被 1000 个事务串行

-- 拆桶
stock_bucket(item_id, bucket_id, count)
-- 1000 个事务分到 10 个 bucket → 单 bucket 100 个串行
-- 库存查询时 SUM(count) GROUP BY item_id
```

桶之间必须守恒：各桶初始库存之和等于总可售库存，每次扣减只作用于一个桶，补偿也回到原桶；某桶空了不代表全部售罄。跨桶借库存、全局限购、订单路由和扩容迁移会增加协调成本。按 userId 分订单库，不会自动解决按 itemId 聚集的库存热点，两种分片键必须一起设计。

#### 原子落单：SQL 条件更新只是事务中的一步

假设请求账本、库存与订单在同一事务边界，消费者首先锁定请求记录并检查状态；以下为参数化 SQL 流程片段：

```sql
BEGIN;
SELECT status, item_id, quantity
FROM purchase_request
WHERE request_id = :request_id
FOR UPDATE;

UPDATE inventory
SET available = available - :quantity
WHERE item_id = :item_id AND available >= :quantity;
```

应用必须在进入事务前校验数量为正整数，并从账本读取可信商品与数量。请求已终态则不再扣减；库存 UPDATE 影响 1 行时才插入订单并更新请求为 SUCCEEDED，在**同一个事务**提交。库存不足时记录 REJECTED，不创建订单；唯一约束或其他 SQL 失败时回滚整个事务，不能吞异常后提交已扣的库存。

订单对 requestId 建唯一约束，业务限购另设合适的唯一键或配额事务；只对消息 ID 去重不足以阻止同一业务被生产成两条不同消息。跨库时不能假设这些 SQL 仍原子，需要明确库存服务的预留/确认/取消协议，见 [分布式事务](./distributed-transaction)。

## 关键陷阱与对策

### 陷阱 1：超卖（最经典）

**原因**：把非原子的读后写当成库存裁决，或遗漏重试去重、主从切换丢写、错误补偿、重建库存覆盖在途预留等故障路径。

**对策**：
1. 前置预留使用条件脚本和 requestId 去重，不允许缺失 key 被当作合法库存。
2. 权威数据库条件扣减与订单创建同事务，重复请求不重复扣减。
3. 预热/重建要有库存代次与业务水位，不能用旧快照覆盖正在扣减的计数；旧代次补偿不得加到新代次。

### 陷阱 2：少卖

**原因**：用户支付超时取消、消息消费失败但没回滚库存。

**对策**：
1. **延迟任务**：按约定到期时间尝试 `UNPAID -> CLOSED` 条件转移，只有成功转移的事务才释放对应库存，重复任务无副作用。
2. **对账 Job**：逐 requestId / reservationId 核对持久账本、订单与库存，不根据一个总差值直接 INCR。发布延迟和在途订单本来就会制造暂时差异。

### 故障窗口矩阵：每一步都要有恢复者

| 故障点 | 能否直接重试/回滚 | 正确恢复 |
|--------|------------------|----------|
| Redis 已预留，写请求账本失败 | DB 提交结果可能未知 | 先按 requestId 查询；明确未受理后幂等释放临时资格 |
| 账本提交成功，响应丢失 | 可以用相同 key 重试 | 重放受理/终态结果，不重复插入或预留 |
| MQ 发送超时 | 不能认定消息未送达，也不能直接退库存 | Outbox 保留事件，用原 eventId 重试；消费者幂等 |
| 消费者扣库存后、提交前崩溃 | 本地事务应回滚 | 重投后重新检查请求状态并执行事务 |
| DB 已提交，消费 ACK 丢失 | 消息可能再次投递 | 检查请求终态/唯一约束，跳过业务后 ACK |
| 支付成功与关闭任务同时到达 | 不能两个分支都更新成功 | 数据库状态机裁决；外部支付已成功但本地已关闭时进入退款/人工对账协议 |
| 临时预留 key 到期 | 不能据此认定订单已取消 | TTL 只是缓存生命周期，业务终态由持久状态和条件转移决定 |

库存生命周期可以表示为 `AVAILABLE -> RESERVED -> SOLD`，未支付取消走 `RESERVED -> RELEASED`。这里的 RESERVED 应是权威预留，不等于 Redis 前置资格；每次转移记录预留 ID、数量、代次与原因，补偿只执行一次。对外状态与内部库存状态分别建模，不把“消息已经 ACK”当作“用户已经支付”。

### 陷阱 3：黄牛刷单

**对策**：
1. **风控前置**：账号年龄 / 设备指纹 / 行为评分
2. **验证码 / 答题**：CDN 层降速
3. **限购规则**：单账号 / 单 IP / 单设备每场限购数量
4. **延迟揭晓**：预约抽签（小米早期）—— 把"先到先得"改成"先约后抽"，本质是把瞬时洪峰摊平到几小时

### 陷阱 4：DB 写放大（社交场景）

**微博发帖**：你发 1 条 → 推给 1000 follower 的 timeline → **DB 要写 1000 次**

**对策**：详见 [设计 Twitter](../data-structures-and-algorithms/hash/twitter-design#业界-feed-流的三大模型)
- **推模型**：写时扇出（适合普通用户）
- **拉模型**：读时聚合（适合大 V）
- **推拉结合**：Twitter / 微博生产方案

## 流量估算速查表

| 要估算的量 | 计算与观察方法 |
|------------|----------------|
| 入站尝试 | 峰值用户操作率 × 每操作尝试数，单独统计重试 |
| 临时预留吞吐 | 单热点脚本耗时、返回大小和分片倾斜，不只测不同 key 的 DECR |
| 持久受理吞吐 | 请求账本与 Outbox 的写放大、唯一索引冲突、日志刷盘 |
| 业务落库吞吐 | 每个事务的 SQL/索引写数、库存锁等待、连接池和副本延迟 |
| 队列容量 | 峰值净积压 × 消息大小，再计副本和保留窗口 |
| 故障后恢复时间 | 积压 / 净消化速率，并校验恢复期间 DB 是否仍有余量 |
| 每成功订单成本 | 临时尝试、重复事件、日志、索引及后台补偿的总资源成本 |

## 典型案例剖析

### 案例 1：双 11 秒杀（淘宝 / 京东）

以下是电商大促的模拟设计题，不代表相关公司的内部实现或实测数据。

**目标**：100w 用户抢 1000 件商品。

**架构**：
```
1. 提前 1 小时预热：商品页静态化推 CDN、库存写入 Redis
2. 流量到达：静态资源走 CDN，服务端风控与限流，Redis 条件预留
3. 通过筛选的请求可靠写入账本与 Outbox，再异步消费，按压测结果限速
4. 超时关闭与支付竞争由订单状态机裁决；库存释放、重复投递与对账均幂等
```

**关键指标**：
- 用户感知延迟：< 1s 看到结果（pending / 售罄）
- 假设消费者处理率为每秒 200 个事务，实际 SQL QPS 还需乘事务写放大
- 验收目标：权威库存不为负，重复请求不重复落单；通过故障注入和对账验证，不从架构图直接宣布零资损

### 案例 2：12306 抢票

**特点**：用户量大、车票库存按车次 × 区段切分、强一致要求高（不能超卖）。

**关键设计**：
- **入站治理**：预约、排队、配额与风险控制减少瞬时竞争，具体策略是题设，不推断实际系统内部实现
- **余票分车次缓存**：Redis 按车次分片，热门车次单独再拆桶
- **下单串行化**：同一个车次的同一区段的票，DB 行锁串行扣减
- **支付超时**：到期时间以业务规则为准，延迟任务触发条件关闭，重复与迟到回调必须可处理

### 案例 3：微信红包

**特点**：单个红包总额固定、N 个人抢、不能超发。

**核心算法**：
- **预拆分**：发红包瞬间就拆好 N 份金额（不是抢时实时算）
- **Redis List PUSH/POP**：N 份金额放 Redis List，抢一份 LPOP 一份
- **抢完即结束**：List 为空时直接返回"晚了一步"，根本不到 DB

详见 [微信红包系统](./interview-cases/wechat-red-packet)。

## 面试常问 & 怎么答

### "秒杀系统怎么设计"

5 步答题模板（30 秒能说完）：
1. **定**：明确库存不变量、受理语义和允许等待时间。
2. **挡**：服务端风控、限流与 Redis 条件预留，保留稳定 requestId。
3. **记**：持久账本与 Outbox 可靠受理后返回 pending，队列有上限。
4. **写**：消费者按数据库安全容量执行幂等落单与权威库存事务。
5. **复**：状态机处理超时释放，失败按事件重试、死信、对账和告警恢复。

### "Redis 预扣库存为什么不超卖"

必须先限定问题：条件 Lua 能在当前主节点上避免并发检查与扣减交错，`DECR` 本身甚至允许负数。端到端不超卖还需考虑重试、复制丢写、补偿和库存重建，最终由权威库存事务维护不变量，不能只回答“Redis 单线程”。

### "MQ 挂了怎么办"

Outbox 保留待投递事件，限制新受理并向用户暴露明确状态；发送超时按结果未知处理，不盲目释放资格。是否切同步直写必须预先压测、限流并复用同一幂等协议，否则故障路径会压垮 DB，甚至与恢复后的消息重复落单。Redis 临时预订单不是消息可靠性的最后防线。

### "怎么防止超卖"

3 层防线：
1. 前置条件预留减少无效竞争，并对 requestId 去重。
2. 权威数据库条件更新、订单唯一约束与状态转移在同一事务边界维护不变量。
3. 幂等释放和逐预留对账处理遗漏；对账不能撤销已对外承诺的超卖，因此不是正确性主防线。

### "为什么不直接 DB 行锁串行"

单热点行会串行竞争，但具体容量取决于事务时长与硬件。先把无效流量挡在数据库之前，再按允许的等待时间控制并发；低规模直接使用短数据库事务可能更简单可靠，只有实测热点瓶颈才引入预筛选、库存分桶或异步流水线。

### "推 vs 拉 vs 推拉结合，发微博怎么选"

详见 [设计 Twitter](../data-structures-and-algorithms/hash/twitter-design#业界-feed-流的三大模型)：
- 普通用户（< 1w follower）→ 推模型，写入 follower inbox
- 大 V（> 1w follower）→ 拉模型，follower 读时实时聚合
- Twitter / 微博生产用推拉结合
